# Интеграция Voice и Core

Будущий сервис Voice AI передаёт события в FastAPI по HTTP. Core присваивает постоянный `call_id`, сохраняет контекст, очередь, назначения и команды в общей SQLite. SIP, LiveKit и проверка фактического аудиосоединения относятся к сервису Voice. [OpenAPI 0.2.1](../contracts/openapi.json)

## Подключение Voice

FastAPI включает Contact Center Core по умолчанию. Новый файл SQLite готовится при запуске. Для существующих баз предусмотрена отдельная миграция. [Миграция SQLite](DATA_MODEL.md#миграция-sqlite)

При будущем подключении Voice задайте `IRIS_VOICE_TOKEN` в обоих процессах и передавайте `Authorization: Bearer <токен>` в запросах. Для связи между хостами используйте HTTPS. Кабинеты используют сессионный cookie `iris_session`. Токены совместимого API оператора задаются отдельно через `IRIS_OPERATOR_TOKENS`.

Все пути ниже используют префикс `/api/v1/voice`. API отвечает `503`, пока сервисный токен не задан, и `401` при неверном токене запроса. При `IRIS_CONTACT_CENTER=0` маршруты Voice отключаются. `404` также означает, что нужная запись недоступна для указанного `call_id`. `409` указывает на конфликт состояния или содержимого повтора, `422` указывает на ошибку валидации.

## Входящий звонок и CRM

| Метод и путь | Запрос и результат |
| --- | --- |
| `POST /calls` | `provider_call_id`, необязательный `caller_phone`. Возвращает `Call` с постоянным `id`, который используется в остальных маршрутах. Используйте один `provider_call_id` для повторных событий одного вызова. |
| `POST /calls/{call_id}/connected` | Voice сообщает, что абонент подключён и может говорить с ИИ. Core переводит `ringing` в `active` с фазой `ai_active`. |
| `POST /calls/{call_id}/identify` | `account_id` и `apartment`. Возвращает объект с полем `identified`. Для повторной проверки другого счёта Core требует принадлежность тому же клиенту. |
| `GET /calls/{call_id}/account` | Текущие данные подтверждённого счёта из CRM для активного звонка. |
| `POST /calls/{call_id}/messages` | `event_id`, `speaker` (`customer`, `assistant` или `operator`), `text`, необязательный `created_at` с часовым поясом. Возвращает сохранённую реплику. |
| `POST /calls/{call_id}/summary` | `event_id` и `summary`. Возвращает текущую карточку `Call`. Новая сводка требует повторной проверки оператором. |
| `POST /calls/{call_id}/ticket` | `handoff`, `confirmation_message_id`, `department` и необязательный `account_number`. Возвращает существующее или новое обращение после подтверждения абонентом. `confirmation_message_id` берётся из ответа API для реплики абонента в этом звонке. Создание обращения и постановка звонка в очередь выполняются отдельными запросами. |

`handoff` для заявки использует существующие поля `ticket_id`, `customer_request`, `summary`, `customer_report`, `verified_facts`, `open_question`, `secondary_questions` и `confirmed_at`. Поля `assumptions` и `actions_taken` принимают списки строк и по умолчанию пусты. Core выставляет `confirmed_at` по сохранённой реплике. Используйте один `ticket_id` при повторе той же операции.

## Передача оператору

1. Отправьте `POST /calls/{call_id}/handoff` с уникальным `event_id` и, при наличии, `department`, `category`, `priority`, `required_skills`. Core добавит звонок в живую очередь и распределит его при наличии подходящего оператора.
2. Читайте `GET /calls/{call_id}/assignment` для текущего предложения или назначения. Ответ `null` означает, что у звонка сейчас нет назначения. Кабинет подтверждает принятие через операторский API, после чего фаза звонка переходит в `operator_joining`.
3. Читайте `GET /calls/{call_id}/commands`, выполните команды через Voice и подтвердите обработку каждой командой `POST /calls/{call_id}/commands/{command_id}/ack`. Сохраняйте `command_id` как ключ идемпотентности в Voice, чтобы повторная доставка не повторяла действие над аудио.
4. После фактического соединения абонента и оператора вызовите `POST /calls/{call_id}/assignments/{assignment_id}/connected`. Только подтверждение Voice переводит Core в `with_operator`. Если подключение сорвалось, вызовите `POST /calls/{call_id}/assignments/{assignment_id}/failed` для возврата звонка в очередь. Используйте идентификатор конкретной попытки.
5. Когда абонент отключится или разговор закончится, отправьте `POST /calls/{call_id}/finish` с `status` (`completed`, `abandoned` или `failed`) и `outcome` (`unknown`, `answered`, `ticket_created`, `unresolved` или `no_confirmation`). Core освобождает очередь и назначение в одной транзакции с завершением звонка. Сохранённое обращение остаётся в своём статусе.

| `kind` команды | Действие Voice |
| --- | --- |
| `connect` | Подготовить аудиоподключение оператора из `payload.employee_id`. Фактическое соединение подтвердить для этого `assignment_id`. |
| `cancel_connect` | Закрыть ресурсы сорвавшейся или просроченной попытки подключения с этим `assignment_id`. |
| `hold`, `resume` | Поставить разговор на удержание или возобновить его. |
| `transfer` | Освободить подключение текущего оператора и подтвердить команду. После подтверждения Core ставит звонок в очередь `payload.department`. Если указан `payload.target_employee_id`, предложение получит этот сотрудник. |
| `end` | Завершить аудиосессию, подтвердить команду и отправить `/finish` с итогом звонка. |

## Повторы и события кабинета

- Повтор регистрации возвращает тот же `call_id`. Повтор реплики с тем же `event_id` возвращает первоначально сохранённую реплику. Повтор сводки с тем же `event_id` возвращает текущий `Call` без записи исходного значения поверх новой сводки. Для нового содержимого создавайте новые идентификаторы событий.
- Поток руководителя доступен через `GET /api/v1/events`, поток оператора по браузерной сессии через `GET /api/v1/operator/events`, поток Bearer-интеграции через `GET /api/v1/contact-center/events`. Кабинет обновляет связанные ресурсы и передаёт `Last-Event-ID` при переподключении. Свежие снимки очереди и назначения доступны через REST.
- Для проверки интеграции запустите Backend на временной SQLite и используйте `PYTHONPATH=backend` для `python -m unittest discover -s backend/tests -v`. Проверку фактического звука проводят с подключённым Voice и настроенной телефонией.

## Сквозная проверка с телефонией

1. В сервисе Voice настройте входящий SIP-вызов и комнату LiveKit. Храните параметры доступа в окружении Voice. Свяжите комнату с постоянным `call_id` из Core.
2. Реализуйте отправку событий звонка, чтение и подтверждение команд. Храните соответствие `assignment_id` попытке медиаподключения и обрабатывайте запоздалые подтверждения по идентификатору конкретной попытки.
3. Подключите браузер оператора к комнате по ограниченным по времени полномочиям. После подтверждения двустороннего аудио отправьте событие подключения в Core. При отказе микрофона, обрыве или тайм-ауте отправьте событие сбоя.
4. Проверьте входящий звонок, передачу того же разговора оператору, двусторонний звук, удержание, перевод, завершение и возврат в очередь при сбое. Сверьте статусы в обоих кабинетах.
